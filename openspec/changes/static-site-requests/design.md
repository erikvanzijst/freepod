## Context

See proposal.md for why. The facts this design rests on:

- **Railpack serves static sites with Caddy, and nothing else.** In the pinned v0.36.4,
  the `staticfile` provider and the Node SPA path both set the plan's deploy start
  command, hardcoded: `caddy run --config Caddyfile --adapter caddyfile 2>&1` and
  `caddy run --config /Caddyfile --adapter caddyfile 2>&1` respectively. A project can
  replace Caddy's config file but not the server. A custom start command turns the SPA
  path off.
- **The plan exists at build time.** The builder runs `railpack prepare … --plan-out
  railpack-plan.json` before building. A Dockerfile build skips Railpack and has no
  plan.
- **Measured idle usage.** Kubelet working set of the static sites running on Railpack's
  Caddy: 7-day medians of 10.1–11.3 MiB and 7-day peaks of 10.2–14.0 MiB.
- **The builder reports through its termination message**, a JSON object the worker
  parses for `image` and `usage`. The container holds no credential and writes nowhere
  else.
- **A release records the build it ships.** `deployment_release.build_id` is what the
  client names on deploy. An update that omits it carries the applied release's build
  forward only while that build's image is still among the values, so the release
  stops claiming a build once the image changes.
- **System overrides win.** `merge_values_scoped` applies the reconciler's overrides
  after the user values, and the `custom` template schema is closed. Together these
  are what `caelus.owner.id` already relies on.

## Goals / Non-Goals

**Goals:**

- A static-site build's app container requests about what Caddy uses at idle.
- The verdict is platform-held. No tenant input sets it or carries it to the chart.
- Everything else renders exactly the 128Mi it does today.

**Non-Goals:**

- Backfilling builds that finished before this ships. They have no stored plan, and a
  rebuild classifies them.
- Sizing other runtimes, or the placeholder, by their measured usage.
- Limits of any kind.

## Decisions

### D1: Detect from the plan's start command, matched exactly

`serves_static_site(plan)` is true only when the plan's `deploy.startCommand` is
exactly one of the two commands Railpack's static providers emit. Anything else is
false: a missing or unreadable plan, a non-object, a missing `deploy` or start command,
a non-string value, or any other command. A Dockerfile build is false without looking.
Detection never fails a build.

*Alternatives considered:*

- *Prefix match on `caddy run`.* This also accepts a start command a tenant wrote
  themselves (`caddy run … & node server.js`), which runs something besides Caddy.
- *Railpack's detected provider (`--info-out`).* The provider is not what runs. A
  custom start command overrides it, and the plan is the result after that override.
- *The pushed image's `Cmd`, read at reconcile time.* This would also classify old
  builds, but the reconciler would need registry reads on every apply. It would also
  replace a structural signal from the tool that built the image with one inferred from
  its output.

The exact strings are coupled to the Railpack version, like the frontend digest
already is. A bump that changes them makes static sites fall back to 128Mi, which is
safe. The builder tests use real plans generated by the pinned version, so the
mismatch shows up there.

### D2: Reported with the image, stored as a non-null boolean on the build

On success the termination message carries `"static_site": true|false` beside
`image`. The worker accepts only a JSON `true` as true and stores the result in
`build.static_site`. The column is `NOT NULL DEFAULT false`, so builds from before
this change, from an older builder image, and failed builds all read as not static.
There is no "unknown" state, because unknown is treated the same as non-static
everywhere.

The verdict is not exposed through the build API. It is a sizing input, not a
property tenants act on.

### D3: The reconciler projects the release's build, not a lookup by image

Every apply injects `caelus.build.staticSite`, and also `caelus.build.image` when the
release names a succeeded build. The values come from the build the desired release
records. `staticSite` is emitted even when false, so a system override always holds
the key, whatever any template schema allows.

*Alternative considered:* look the image up among the owner's builds by digest. That
would add a second provenance rule beside the one the release ledger already applies.
The ledger's rule already drops a build the release no longer runs.

### D4: The chart decides, by comparing the image it runs

The chart uses `staticSiteResources` only when `image` is non-empty, `caelus.build.staticSite`
is true, and `caelus.build.image` equals `image`. Otherwise it uses `resources`.

Only the chart knows which value is the image it runs. The release ledger finds an
image "by value, never by key", and that rule is too weak here. The `custom` schema
also accepts arbitrary strings, in `auth.public`. A tenant could name a static build
on deploy, place its image string there, and run a different image. That would get a
static release under a value-based check. The equality check in the chart closes
this.

*Alternative considered:* the reconciler overrides `resources.requests.memory`
directly. Rejected for two reasons. It puts one chart's value layout into the generic
reconciler, outside the `caelus` namespace that is the reconciler's to write. It
would also make the request invisible from the chart's own values.

### D5: 16Mi memory, CPU unchanged

Requests are the idle billing floor, so they are sized to median idle usage rounded
just above, not to peak plus headroom. Median idle is 10–11 MiB. 16Mi is the next
round size above it, leaves about 5 MiB of margin for Caddy's buffers and Go heap
growth under light load, and covers every observed 7-day peak (at most 14 MiB). Usage
above the request is billed as usage, and nothing is limited, so a busier site costs
what it uses and is never killed for exceeding its request. CPU stays at 10m, the
same floor every `custom` app has.

32Mi was considered. It roughly triples the floor of a site that has not been seen
above 14 MiB, and buys nothing that usage billing does not already cover.

## Risks / Trade-offs

- [A tenant forces Caddy's exact start command through `railpack.json` to get the
  smaller request] → Then the container does run Caddy: the start command is the
  process. A Caddyfile cannot start another program with stock Caddy. Even a gamed
  verdict gains nothing beyond a lower floor. Usage above it is billed, no limit
  changes, and any `custom` app can already exceed its request.
- [Page cache counts toward working set, so a static site serving large, frequently
  read assets can exceed 16Mi] → This is billed as usage. A request is a scheduling
  floor, not a cap, and the amounts are a few MiB per pod.
- [A Railpack bump changes the start command strings] → Static sites fall back to
  128Mi (D1). Regenerating the test plans with the new version catches it.
- [Deployments built before this change stay at 128Mi] → They shrink on their next
  build and deploy. That is also what moves them onto the new chart.

## Migration Plan

1. Merge. The migration adds `build.static_site` with default false. Every existing
   build reads as not static.
2. Publish builder image 0.5.0 and the `custom` chart 0.14.0. The chart must exist
   before the rollout whose catalog apply points the `custom` template at it.
   Otherwise deployments moving to the new template fail to pull it.
3. Roll out the API and workers (migration, catalog), then the `builder_image`
   Terraform pin. Either order works for the builder: an old worker ignores the extra
   field, and a new worker treats its absence as not static.
4. Existing static sites switch to 16Mi on their next `freepod deploy`.

Rollback: revert the catalog to chart 0.13.0. That chart ignores `caelus.build`, so
every app renders 128Mi again. The column and the termination field are inert
without the chart.
